Annonation vs xml 
--------------------------
-----------------------------------------------------------------------------------------------
| Feature                    | Annotation                     | XML                            |
------------------------------------------------------------------------------------------------
| Location of Config         | Inside Java code using         | In external XML files          |
|                            | @annotations                   | (e.g., applicationContext.xml) |
------------------------------------------------------------------------------------------------
| Readability                | Easy to read in code           | Clear separation of config     |
------------------------------------------------------------------------------------------------
| Flexibility                | Less flexible after compile    | Easy to change without code    |
------------------------------------------------------------------------------------------------
| Ease of Refactoring        | Refactoring-friendly           | Needs to sync class names      |
------------------------------------------------------------------------------------------------
| Separation of Concerns     | Less separation (in code)      | Full separation from logic     |
------------------------------------------------------------------------------------------------
| Compilation Dependency     | Needs recompilation on change  | No recompilation needed        |
------------------------------------------------------------------------------------------------
| Suitable For               | Small to mid-size projects     | Large enterprise applications  |
------------------------------------------------------------------------------------------------
| Maintenance                | Harder to maintain in large    | Easier in large teams/projects |
|                            | projects due to inline config  |                                |
------------------------------------------------------------------------------------------------
| Learning Curve             | Simpler for Java developers    | Requires understanding of XML  |
------------------------------------------------------------------------------------------------
| Tool Support               | Limited (inline)               | XML tools and editors support  |
------------------------------------------------------------------------------------------------
| Example                    | @Component                     | <bean id="..." class="..."/>   |
|                            | @Autowired                     | <property name="..." ... />    |
------------------------------------------------------------------------------------------------
| Dynamic Config at Runtime  | Difficult                      | Easy                           |
------------------------------------------------------------------------------------------------
| Code Portability           | Tightly coupled                | Loosely coupled                |
------------------------------------------------------------------------------------------------

Conclusion:
- Use **Annotations** when you want speed, simplicity, and proximity to the logic.
- Use **XML** when you need configuration externalization, flexibility, and modular deployment.

THREAD POOL 
-------------------

What is a Thread Pool?
-------------------------
A Thread Pool is a group of pre-instantiated reusable threads. Instead of creating a new thread every time, tasks are assigned to threads in the pool.

It helps:
- Improve performance
- Reduce resource consumption
- Provide better system stability under load

------------------------------------------------------
Why Use Thread Pool?
-------------------------
✔ Avoids overhead of thread creation
✔ Reuses threads
✔ Limits number of concurrent threads
✔ Prevents resource exhaustion

------------------------------------------------------
Core Interfaces & Classes (java.util.concurrent)
------------------------------------------------------
🔸 Executor               - Basic interface
🔸 ExecutorService        - Provides more control
🔸 Executors              - Factory for creating pools
🔸 ThreadPoolExecutor     - Main implementation
🔸 Future<T>              - Result of asynchronous computation



JDBC API DRIVER
-------------------

What is a JDBC Driver?
--------------------------
A JDBC Driver is a software component that enables Java applications to interact with databases using the JDBC API (Java Database Connectivity).

There are **4 types of JDBC Drivers**, also known as **API Drivers**.

Types of JDBC Drivers
-------------------------

Type-1: JDBC-ODBC Bridge Driver
------------------------------------
🔹 Translates JDBC calls into ODBC (Open Database Connectivity) calls.
🔹 Requires ODBC driver installed on client machine.

Pros:
✔ Easy to use for testing
✔ No need for vendor-specific driver

Cons:
✘ Platform dependent
✘ Performance is poor
✘ Deprecated in Java 8 and removed in Java 9+

🔸 Example:
Class.forName("sun.jdbc.odbc.JdbcOdbcDriver");
Connection con = DriverManager.getConnection("jdbc:odbc:DSNName");

Type-2: Native-API Driver
------------------------------
🔹 Converts JDBC calls into native database calls using C/C++ libraries.

Pros:
✔ Better performance than Type-1

Cons:
✘ Platform dependent
✘ Requires native DB libraries on client

🔸 Example:
Oracle thin driver with native libraries.

Type-3: Network Protocol Driver (Middleware)
-------------------------------------------------
🔹 Converts JDBC calls into a network protocol.
🔹 Communicates with middleware server, which in turn talks to the DB.

Pros:
✔ No client-side DB libraries needed
✔ Platform independent

Cons:
✘ Requires middleware setup

Type-4: Thin Driver / Pure Java Driver
-------------------------------------------
🔹 Converts JDBC calls directly into database-specific protocol.
🔹 Fully implemented in Java — no native code.

Pros:
✔ Platform independent
✔ High performance
✔ Most commonly used (e.g., MySQL, PostgreSQL)

🔸 Example:
Class.forName("com.mysql.cj.jdbc.Driver");
Connection con = DriverManager.getConnection(
  "jdbc:mysql://localhost:3306/db", "root", "password");

JDBC Driver Summary Table
----------------------------

| Type  | Name               | Platform Independent | Performance | Client Library Required |
|-------|--------------------|----------------------|-------------|--------------------------|
| 1     | JDBC-ODBC Bridge   | ❌ No                | 🟠 Poor     | ✅ Yes                   |
| 2     | Native API Driver  | ❌ No                | 🟡 Medium   | ✅ Yes                   |
| 3     | Network Protocol   | ✅ Yes               | 🟡 Medium   | ❌ No                    |
| 4     | Thin Driver        | ✅ Yes               | 🟢 Best     | ❌ No                    |


Which Driver is Best?
-------------------------
➡ For modern applications, **Type-4 (Thin Driver)** is the most recommended.
✔ Platform independent
✔ No external library required
✔ Actively supported

Common JDBC Type-4 Driver Class Names
----------------------------------------
🔹 MySQL:       com.mysql.cj.jdbc.Driver
🔹 Oracle:      oracle.jdbc.driver.OracleDriver
🔹 PostgreSQL:  org.postgresql.Driver
🔹 SQL Server:  com.microsoft.sqlserver.jdbc.SQLServerDriver

Conclusion
--------------
A JDBC driver acts as a bridge between Java apps and databases. Knowing the types helps you choose the best one for your application's needs.
